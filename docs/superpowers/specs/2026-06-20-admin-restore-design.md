# Admin 端 1:1 还原设计

## 背景

当前项目的 C 端页面已经完成 React 化，Admin 端也已接入基础路由与权限守卫，但实际内容仍停留在占位阶段。现有后台仅包含一个极简 `AdminLayout` 和 5 个占位页面，和线上参考页 `https://lessons-web.github.io/irbtree-management-system/admin.html` 在信息架构、页面数量、导航层级、交互容器与视觉表现上存在明显差距。

本次工作的目标不是重新设计后台，而是以线上 `admin.html` 为唯一视觉与结构参考，在当前 React 工程中完整还原一套桌面端 Admin 后台。

## 目标

- 将当前 `src/admin` 从占位后台升级为完整可浏览的桌面端管理后台
- 按线上原型拆出独立导航与页面，而不是保留当前 5 个分组占位路由
- 1:1 还原后台壳、顶部栏、侧边栏、表格页、筛选区、分页、抽屉、弹窗和状态标签等视觉结构
- 通过本地 mock 数据支撑全部页面的静态展示与基础前端交互
- 在不接入新接口的前提下，让后台页面达到可演示、可继续迭代接接口的状态

## 非目标

- 不接入真实后台 API
- 不在本次处理移动端或平板端精细适配
- 不追求超出线上原型的新视觉设计
- 不重做现有 C 端信息架构
- 不在本次引入复杂状态管理或持久化方案

## 还原范围

本次按“完整 1:1 视觉与交互结构还原”执行，范围包括：

- 后台左侧导航、系统设置子菜单、侧栏折叠
- 后台顶部栏、页面标题、通知入口、管理员菜单、切换到用户端入口
- 9 个管理页面的独立路由与页面壳
- 每个管理页中的筛选条、主操作按钮、数据表格、状态标签、分页区
- 新增/编辑抽屉、确认删除弹窗、通知抽屉等容器层交互

本次不以“业务真实可提交”为验收口径，而以“桌面端还原度 + React 结构可维护性”为主要目标。

## 目标页面与路由

后台路由不再保留当前的 5 个占位分组，而是直接展开为线上原型对应的页面结构：

- `/admin` 或 `/admin/courses`：课程管理
- `/admin/reviews`：评价管理
- `/admin/universities`：院校管理
- `/admin/teachers`：教师管理
- `/admin/semesters`：学期管理
- `/admin/tags`：标签管理
- `/admin/users`：用户管理
- `/admin/messages`：消息管理
- `/admin/logs`：系统日志

其中 `/admin` 默认重定向到 `/admin/courses`，保持进入后台后即落在主页面的体验。

## 设计原则

### 1. 原型优先

以 `docs/admin.html` 的信息架构、布局比例、按钮位置、表格栏目与状态样式为最高参考，不对页面重新分组，不引入新的导航逻辑。

### 2. 组件化还原

虽然目标是 1:1 还原，但实现方式不采用“逐页硬搬 HTML”，而是按后台通用结构提炼 React 组件，再用页面配置与 mock 数据拼装各个页面，以避免 `src/admin` 演变为难维护的大文件集合。

### 3. 桌面端优先

本次只对桌面端体验负责。窄屏下允许页面仅保持基本可访问，不作为验收重点。

### 4. 数据展示优先

页面搜索、筛选、分页、状态切换等交互以本地前端状态驱动，强调页面观感和交互流畅度，不要求和真实后端语义完全一致。

## 架构设计

### 目录结构

建议将后台拆分为以下层次：

- `src/admin/layouts`
  - 放置后台整体布局、侧边栏、顶部栏、通知抽屉
- `src/admin/components`
  - 放置后台复用组件，例如筛选条、表格容器、状态标签、分页槽位、表单抽屉内容块
- `src/admin/pages`
  - 9 个页面按模块拆分，每页只负责组装页面内容
- `src/admin/data`
  - 放置每个页面对应的 mock 列表、筛选项、统计信息和表单初始值
- `src/admin/types`
  - 放置后台专属类型定义，如课程行、评价行、用户行、消息行等
- `src/admin/config`
  - 放置导航配置、页面标题映射、状态文案映射等纯配置内容

### 路由设计

`src/app/router.tsx` 中的后台路由改为独立页面映射，并继续挂在 `RequireRole anyOf={['admin', 'teacher']}` 之下。

后台入口层次为：

- `RequireRole`
- `AdminLayout`
- 具体管理页路由

不再使用当前 `DashboardPage` 与 4 个占位分类页作为最终 IA。

### 布局壳设计

后台布局拆成三块：

- 左侧 `AdminSidebar`
  - 负责主导航、高亮态、系统设置子菜单、折叠态与底部版本区
- 顶部 `AdminHeader`
  - 负责页面标题、通知按钮、管理员菜单、切换用户端入口与退出登录入口
- 内容区 `AdminPageShell`
  - 负责统一页面留白、滚动区域与页面标题以下的通用间距

这样可以让各页面聚焦于内容本身，不重复书写壳层样式。

## 共享组件设计

建议优先抽出以下后台共享组件：

- `AdminSidebar`
- `AdminHeader`
- `AdminPageShell`
- `AdminActionBar`
  - 承载搜索框、下拉筛选和主按钮
- `AdminTableCard`
  - 统一表格容器、表头背景、边框和横向滚动
- `AdminStatusBadge`
  - 统一启用、停用、已处理、待审核等状态样式
- `AdminEmptyState`
  - 处理筛选后为空或页面无数据的展示
- `AdminNotificationDrawer`
  - 还原右上角通知侧抽屉
- `AdminFormDrawer`
  - 基于现有通用 `Drawer` 封装后台右侧抽屉壳
- `AdminConfirmModal`
  - 基于现有通用 `Modal` 封装删除/下线确认弹窗

现有 `src/components/common/Drawer.tsx`、`Modal.tsx`、`Pagination.tsx` 可被后台复用，但需要通过后台包装组件统一外观，避免直接在每个页面散落定制样式。

## 页面映射设计

### 课程管理

作为后台默认首页，页面包含：

- 搜索课程代码或名称
- 院校筛选
- “新增课程”按钮
- 课程表格
- 状态列和操作列
- 新增/编辑课程抽屉

该页面优先承接原型中的完整表格视觉和后台主工作流。

### 评价管理

页面包含：

- 关键词搜索
- 评分或处理状态筛选
- 批量治理或单条处理操作入口
- 评价列表表格
- 详情查看或处理弹窗/抽屉

### 院校管理

页面展示院校基础信息列表、状态标签与新增院校入口。

### 教师管理

页面展示教师姓名、所属院校、教授课程、状态和操作。

### 学期管理

页面展示学期名称、年份、时间范围、状态与维护操作。

### 标签管理

页面展示标签名称、适用范围、使用次数、状态与编辑操作。

### 用户管理

页面展示用户昵称、角色、注册时间、活跃状态、封禁或启用操作。

### 消息管理

作为系统设置子项之一，页面展示站内消息列表、推送状态、创建时间和发送入口。

### 系统日志

作为系统设置子项之一，页面展示操作日志、模块来源、操作者、时间与关键行为摘要。

以上页面均不追求深业务联动，但要求具备和原型一致的表格密度、按钮位置和容器层结构。

## 数据组织设计

后台 mock 数据按页面拆分，避免集中在一个超大文件中。建议采用：

- `courses.ts`
- `reviews.ts`
- `universities.ts`
- `teachers.ts`
- `semesters.ts`
- `tags.ts`
- `users.ts`
- `messages.ts`
- `logs.ts`

每个文件至少包含：

- 列表数据
- 筛选项枚举
- 默认分页信息
- 抽屉表单默认值或详情示例

页面内仅做轻量级筛选、搜索和分页切片，不引入跨页面共享的复杂数据层。

## 数据流与交互

本次后台的数据流以页面本地状态为主：

- 页面加载时读取对应 mock 数据
- 搜索框、下拉筛选通过组件状态驱动列表过滤
- 分页由页面本地分页状态控制
- 抽屉和弹窗仅维护前端可见性与表单展示，不要求真正提交持久化
- 删除、停用、发布等操作以本地乐观更新或提示信息模拟

通知抽屉、管理员菜单、系统设置子菜单、侧栏折叠均由 `AdminLayout` 层统一管理，避免每页重复维护 UI 状态。

## 权限与导航

后台继续复用当前 `RequireRole` 路由守卫，不在本次重做权限体系。

但有一个需要同步收敛的点：

- 当前登录态默认 `canAccessAdmin: true` 的策略过于宽松

本次如果实现过程中发现 student 角色会默认看到后台入口，至少需要把后台入口显示和路由可访问性调整到与角色判断一致，避免还原后的 Admin 被任意账号进入。这属于“与当前目标直接相关的必要修正”，不属于额外重构。

## 错误与空状态

后台页需要具备统一的轻量级异常与空状态处理：

- 筛选后无结果时展示统一空状态卡片
- mock 列表为空时仍保留操作栏和表头结构
- 详情抽屉无对应数据时展示简单提示并可关闭
- 不新增复杂错误边界，只保证页面不因空数据报错

## 测试策略

本次以“关键结构验证”而非“全量页面行为测试”为主，建议覆盖：

- `/admin` 默认跳转到课程管理
- 侧边栏存在 9 个页面入口，系统设置包含 2 个子项
- 任一管理页可正常渲染其标题、操作栏和表格容器
- 管理员菜单包含“切换到用户端”和“退出登录”
- 侧栏折叠和系统设置子菜单展开不会产生运行时错误

如果时间有限，优先补路由与布局级测试；不强求为每张表格增加低价值单测。

## 验证标准

完成后应满足以下结果：

- 打开 `/admin` 可进入完整后台，并默认落在课程管理页
- 左侧导航、顶部栏、通知入口、管理员菜单与线上原型结构一致
- 9 个后台页面均可从路由直接访问
- 每个页面都有接近原型的筛选条、表格区、状态标签、分页和操作按钮
- 抽屉、弹窗、通知面板可被打开和关闭
- 不引入新的 TypeScript、ESLint 或明显运行时错误

## 风险与约束

- `docs/admin.html` 是单文件静态原型，React 化后需要适度提炼组件，因此源码组织不会与原型 DOM 逐行一致，但视觉和交互结构应保持一致
- 原型中的部分细节依赖图标库和静态 HTML 行为，迁移时允许做等价实现
- 由于本次不接真实 API，某些“新增成功”“状态变更”只能以前端模拟反馈呈现
- 如果后台入口权限收敛时影响现有测试，需要同步调整测试预期
