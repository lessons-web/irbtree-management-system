# Admin 第二阶段交互与 1:1 还原设计

## 背景

第一阶段已经将 Admin 端从占位后台升级为 React 版本的完整桌面端后台，完成了：

- 9 个后台独立路由
- 左侧导航、顶部栏、通知抽屉、管理员菜单
- 各页面的筛选条、表格、分页、抽屉和确认弹窗壳
- 基于本地 mock 的静态数据展示

但当前实现仍主要停留在“结构 mock”阶段。页面虽然具备打开抽屉、显示确认框、切换路由和筛选分页的基本外观，但新增、编辑、删除、状态切换、批量处理、日志沉淀与通知反馈还没有形成完整的前端行为闭环。

同时，本阶段不是单纯补逻辑，而是继续以 `docs/admin.html` 为唯一参照，向原系统的交互方式、容器形态和操作反馈做 1:1 靠拢。

## 目标

- 将后台从“结构 mock”升级为“前端可操作的高保真 mock 后台”
- 在不接真实 API 的前提下，为核心页面补齐新增、编辑、删除、状态切换、批量处理等前端逻辑
- 继续对齐 `docs/admin.html` 的交互形态，而不是只保留现有抽屉和弹窗壳
- 将本地操作联动到通知抽屉与系统日志，形成完整的后台操作反馈链
- 保持当前 React + 路由结构不变，避免为第二阶段引入过重的全局状态方案

## 非目标

- 不接入真实后台 API
- 不重做后台信息架构
- 不新增移动端适配目标
- 不引入 Redux、Zustand 或远程缓存层
- 不追求超出 `docs/admin.html` 的业务扩展

## 第二阶段验收口径

第二阶段完成后，后台应达到以下状态：

- 页面中的“新增 / 编辑 / 删除 / 状态切换”不再只是打开 UI，而是会真实更新本地页面状态
- 与 `docs/admin.html` 对应的抽屉、弹窗和详情区块具备接近原系统的字段布局与交互顺序
- 操作完成后会反馈到列表、通知抽屉和系统日志中
- 搜索、筛选、分页、空状态、抽屉开关和确认流转可以稳定协同工作

## 原系统对齐原则

本阶段的 1:1 还原不是重新抄写静态 HTML，而是对齐原系统的交互模式：

### 1. 页面级交互模式对齐

根据 `docs/admin.html`，不同页面采用了不同的容器形态：

- 课程管理：右侧抽屉
- 评价管理：右侧详情抽屉，含评分与标签展示
- 用户管理：右侧抽屉，含角色选择
- 院校、教师、学期、标签：中心弹窗
- 消息管理、系统日志：列表管理页，偏向表格与状态操作

第二阶段应恢复这种页面差异，而不是让所有页面都共用一个“只有静态说明块”的统一抽屉。

### 2. 操作反馈对齐

原系统中新增、删除、编辑等操作会立即反馈到列表，并伴随提示或界面更新。React 版本应实现等价前端行为：

- 新增后立即出现在表格顶部或合理位置
- 编辑后立即更新对应行
- 删除或停用后立即改变状态或从列表移除
- 详情抽屉中的内容与当前行保持同步

### 3. 交互层级对齐

保留原系统的交互层级：

- 行级操作优先在表格内触发
- 查看详情优先走抽屉
- 危险操作必须先确认
- 页面头部主按钮对应“新增”或“批量处理”等主流程

## 方案选择

本阶段采用“通用实体管理层 + 页面特化容器”的方案。

### 方案说明

- 不做全局 mock store
- 不把每页逻辑完全散落在页面内部
- 抽一层后台页面行为模型，统一处理：
  - 本地行数据维护
  - 新增 / 编辑 / 删除
  - 状态切换
  - 筛选后分页修正
  - 提交成功后的通知与日志记录

页面自身只提供：

- 初始数据
- 字段定义
- 过滤规则
- 页面特有的容器类型和表单布局

### 选择原因

该方案同时满足两个目标：

- 让页面真正可操作
- 继续逼近 `docs/admin.html` 的原系统交互差异

同时避免过早引入全局 store 带来的额外复杂度。

## 架构设计

### 页面状态层

为后台新增一个共享的页面行为层，例如：

- `useAdminCrudState`
- `useAdminOperationFeed`
- `useAdminFormMode`

职责如下：

- 管理页面当前行数据
- 管理选中行、抽屉模式、弹窗状态
- 提供 `createEntity`、`updateEntity`、`removeEntity`、`patchStatus` 等统一行为
- 保证筛选条件变化、删除后分页变化、切换数据后当前抽屉内容同步更新

### 操作反馈层

新增一个后台本地操作流，用于沉淀最近操作：

- 最近通知 feed
- 最近日志 feed

数据来源全部是本地前端操作，例如：

- 新增课程
- 编辑用户角色
- 通过评价审核
- 撤回消息
- 归档学期

它们会同时影响：

- 对应页面表格
- 顶部通知抽屉
- 系统日志页面

### 容器分层

恢复原系统的容器差异，而不是所有页面都只用一种 `DetailGroup`：

- 抽屉类页面
  - 课程管理
  - 评价管理
  - 用户管理
- 弹窗类页面
  - 院校管理
  - 教师管理
  - 学期管理
  - 标签管理
- 列表行为类页面
  - 消息管理
  - 系统日志

其中：

- 课程抽屉应是可编辑表单，不再只是说明块
- 评价抽屉应展示详情、评分、标签与处理动作
- 用户抽屉应提供角色选择与状态编辑
- 院校 / 教师 / 学期 / 标签应使用中心弹窗来接近原 HTML 原型

## 页面行为设计

### 课程管理

对齐 `docs/admin.html` 中的课程右侧抽屉：

- 支持新增课程
- 支持编辑课程
- 支持下线课程
- 抽屉中使用真实表单字段
  - 课程代码
  - 课程名称
  - 所属院校
  - 学分
  - 授课教师
  - 助教
  - 课程描述
- 提交后立即更新表格

### 评价管理

对齐原系统中的详情抽屉：

- 支持查看评价详情
- 支持通过 / 驳回
- 支持批量治理的前端状态模拟
- 抽屉中展示：
  - 课程
  - 用户
  - 年份 / 学期
  - 四项评分
  - 标签
  - 评价正文
- 处理后列表状态、通知和日志同步更新

### 院校管理

对齐原系统弹窗模式：

- 支持新增院校
- 支持编辑院校
- 支持删除院校
- 使用中心弹窗维护名称、城市、国家、邮箱和状态

### 教师管理

对齐原系统弹窗模式：

- 支持新增教师
- 支持编辑教师
- 支持删除教师
- 维护教师姓名、院校、课程、职称、邮箱和状态

### 学期管理

对齐原系统弹窗模式：

- 支持新增学期
- 支持编辑学期
- 支持归档 / 删除
- 维护学期名称、年份、时间范围、课程数量与状态

### 标签管理

对齐原系统标签弹窗行为：

- 支持新增标签
- 支持编辑标签
- 支持删除标签
- 维护名称、适用范围、描述、状态

### 用户管理

对齐原系统中的用户抽屉与角色选项：

- 支持新增账号
- 支持编辑账号
- 支持停用 / 删除
- 抽屉字段应包含：
  - 昵称
  - 邮箱
  - 角色
  - 状态
- 角色选择以单选或等价控件表现，贴近原系统的 `user / operator / admin` 选择结构

### 消息管理

在现有页面基础上补齐前端发布流程：

- 支持新建消息
- 支持编辑消息
- 支持撤回消息
- 支持切换状态，例如草稿、已排期、已发送
- 提交后通知抽屉中新增一条“消息已发布 / 已撤回”的本地通知

### 系统日志

系统日志保持只读页，但需要从本地操作流中自动追加记录：

- 模块
- 操作者
- 动作
- 时间
- 结果

不需要支持手工新增或编辑。

## 组件设计

### 保留并增强的组件

- `AdminPageFrame`
  - 增加主操作、次操作与批量操作插槽
- `AdminPageTable`
  - 增加行点击、空状态、行动列配置
- `AdminFormDrawer`
  - 增加 mode、footer actions、submit / cancel 能力
- `AdminConfirmModal`
  - 保持危险操作确认

### 新增组件

- `AdminEntityDialog`
  - 为院校、教师、学期、标签提供中心弹窗壳
- `AdminField`
  - 输入、选择、文本域等统一字段包装
- `AdminReviewRatings`
  - 渲染评价详情中的四项评分
- `AdminOperationToast` 或等价轻量反馈层
  - 如果不单独实现 toast，至少在 UI 上提供成功反馈区域

### 统一行为 Hook

建议增加以下 Hook：

- `useAdminEntityCollection`
  - 管理一组实体的增删改状态
- `useAdminPageFilters`
  - 管理搜索、筛选、分页与页码修正
- `useAdminOperationFeed`
  - 管理通知和日志的本地沉淀

## 数据设计

本阶段仍以本地 mock 为唯一数据源，但数据组织要升级为“可变初始数据”模型。

每页数据分两层：

- 初始静态 seed
- 运行时页面状态

额外增加：

- 评价详情中的评分结构
- 用户角色映射
- 消息状态流转
- 操作日志记录结构
- 通知记录结构

## 数据流

### 新增 / 编辑

提交表单时：

1. 做前端轻校验
2. 更新页面本地行数据
3. 关闭抽屉或弹窗
4. 写入一条本地通知
5. 写入一条系统日志

### 删除 / 停用 / 撤回

确认弹窗确认后：

1. 更新行状态或移除记录
2. 若当前页无数据则修正页码
3. 关闭确认框
4. 写入通知和日志

### 评价处理

评价通过或驳回后：

1. 更新该条评价的 `moderation`
2. 更新状态标签
3. 关闭抽屉或保留抽屉并提示处理完成
4. 写入日志和通知

## 与 `admin.html` 的对应关系

第二阶段需重点对齐以下原型节点：

- 课程抽屉：`course-drawer`
- 评价抽屉：`review-drawer`
- 用户抽屉：`user-drawer`
- 标签弹窗：`tagModal`
- 学期弹窗：`semesterModal`
- 院校弹窗：`universityModal`
- 教师弹窗：`teacherModal`

React 版本不要求 DOM 名称一致，但要求交互角色一致、视觉层级一致、字段组织接近一致。

## 测试策略

第二阶段补充“行为测试”而不是只测路由：

- 课程页新增课程后，表格出现新行
- 用户页停用账号后，状态更新或记录移除
- 消息页新建或撤回后，状态与通知联动更新
- 评价页通过 / 驳回后，状态标签变更
- 日志页能看到来自本地操作流的新记录

继续保留：

- 后台路由测试
- 顶部菜单与系统设置子菜单测试

## 验证标准

完成后应满足以下结果：

- Admin 后台的核心页面均可完成本地 CRUD 或等价状态流转
- 抽屉与弹窗不再只是静态说明块，而是有真实字段与提交逻辑
- 通知抽屉与系统日志页能反映本地操作
- 评价详情抽屉能展示更接近原系统的评分、标签和正文
- 各页面的容器形态与 `docs/admin.html` 保持一致方向
- 不引入新的 TypeScript、测试或构建错误

## 风险与约束

- 本阶段不接后端，因此“成功提示”“状态变更”“消息发送”全部以前端模拟完成
- 原系统中部分按钮通过 `alert` 与 `confirm` 占位，React 版本需要做等价但更稳定的交互实现
- 若将所有页面都做成强抽象表单，容易偏离原系统差异，因此共享行为与页面特化要同时存在
- 第二阶段仍然不处理跨刷新持久化；刷新后数据回到 seed 初始状态属于预期行为
