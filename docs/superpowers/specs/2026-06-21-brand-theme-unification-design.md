# 品牌主题色统一为 brand 体系设计

## 背景

当前项目已经在部分组件中出现了 `brand-*` 类名，但全局实际仍以 `indigo-*` 为主。根样式中还保留了 `--color-primary` 和 `--color-secondary` 两个单点变量，导致主题来源和命名口径同时存在三套表达：

- `brand-*`
- `indigo-*`
- `--color-primary` / `--color-secondary`

这会带来两个直接问题：

- 主题命名不统一，新增页面容易继续混用
- 后续换肤时需要同时修改组件类名和全局变量，维护成本高

本次工作的目标是把项目主色统一收敛为 `brand` 体系，让组件只消费统一的品牌 token，而不再直接依赖 `indigo` 命名或零散的单点变量。

## 目标

- 明确系统主题主色的唯一公开命名为 `brand`
- 在全局主题层建立完整的 `brand` 色阶 token
- 将项目内与主色相关的 `indigo-*` 用法统一迁移为 `brand-*`
- 收敛根样式中的主色变量定义，避免与 `brand` 命名并存
- 在不明显改变当前视觉观感的前提下，为后续换肤提供单一入口

## 非目标

- 不重构所有中性色和语义色
- 不把 `red`、`rose`、`yellow`、`slate` 等语义或中性色一并改成 `brand`
- 不改变页面布局、交互逻辑和业务数据流
- 不在本次引入多套动态主题切换 UI

## 当前状态

当前代码库呈现以下现状：

- 全局基础主色定义在 `src/index.css`
- 实际主色值为 `#4f46e5` 和 `#6366f1`
- 大量页面和组件直接使用 `indigo-*`
- `brand-*` 只在个别位置零散出现，尚未形成真实的主题体系

因此本次不是“补充 brand 命名”，而是“以 brand 为统一主题语义重新收口”。

## 方案选择

本次采用「统一为 `brand` 体系」方案。

### 备选方案

- 统一为 `primary`
- 同时保留 `primary` 和 `brand`

### 不采用原因

`primary` 更适合偏组件库语境的中性命名，而当前需求更强调整站主题与后续换肤入口。若同时保留 `primary` 和 `brand`，短期兼容性虽然更强，但长期会继续制造双轨命名，无法真正解决混用问题。

因此，本次确定：

- 对外主题命名统一为 `brand`
- 组件层只使用 `brand-*`
- 不再继续扩散 `primary` 或 `indigo` 的主题命名

## 设计原则

### 1. 命名唯一

与品牌主色相关的公开样式命名只保留 `brand`。以后新增组件不再出现 `indigo-*` 作为主色表达。

### 2. 视觉稳定

本次先统一来源和命名，不主动追求视觉改版。新的 `brand` 色阶需要尽量贴近当前 `indigo` 观感，避免统一命名时顺带引入大面积视觉波动。

### 3. 换肤优先

组件应尽量只依赖 `brand` token。后续若需要更换整站主色，只调整主题层定义，而不需要回头逐个修改组件类名。

### 4. 改动聚焦

只处理“品牌主色”相关内容，不借机扩展为整套色彩系统重构，避免本次范围失控。

## 主题体系设计

### 主题命名

统一后的主题色命名采用：

- `brand-50`
- `brand-100`
- `brand-200`
- `brand-300`
- `brand-400`
- `brand-500`
- `brand-600`
- `brand-700`
- `brand-800`
- `brand-900`
- `brand-950`

这套色阶将作为项目品牌主色的唯一公开入口。

### 主题来源

在 `src/index.css` 中建立 `brand` 对应的全局主题变量，让 Tailwind v4 可以直接生成并消费 `bg-brand-*`、`text-brand-*`、`border-brand-*`、`from-brand-*`、`to-brand-*` 等类名。

设计要求如下：

- `brand-500` 和 `brand-600` 接近当前主按钮与主强调色
- `brand-50` 到 `brand-200` 用于浅底、高亮背景和轻提示
- `brand-700` 到 `brand-950` 用于标题、选中态、深色按钮和边界强化

### 旧变量处理

当前 `src/index.css` 中的：

- `--color-primary`
- `--color-secondary`

需要收敛处理。原则如下：

- 如果仍有全局基础样式依赖它们，则改为从 `brand` 体系派生
- 如果只用于少量历史用途，则直接移除，改为 `brand` 变量或 `brand-*` 类名

最终目标是避免在代码中继续出现“brand 是一套，primary 又是一套”的并存状态。

## 组件消费规范

统一后，组件层遵循以下规则：

- 主按钮使用 `brand` 色阶
- 主链接高亮、导航选中态、聚焦态和主视觉描边使用 `brand` 色阶
- 渐变、阴影、描边和浅底强调如果表达的是品牌主色，也统一切换到 `brand`
- 不再使用 `indigo-*` 表达品牌主色

示例包括但不限于：

- `bg-indigo-600` → `bg-brand-600`
- `text-indigo-700` → `text-brand-700`
- `border-indigo-200` → `border-brand-200`
- `from-indigo-500` → `from-brand-500`

## 影响范围

本次将影响以下两类位置：

### 1. 全局主题定义

- `src/index.css`

主要负责：

- 建立 `brand` token
- 调整根级主色变量
- 让选择区、全局背景混色等基础样式改为从 `brand` 来源取值

### 2. 组件与页面主色消费

用户端页面、后台页面和通用组件中，凡是以 `indigo-*` 表达品牌主色的地方都需要统一迁移到 `brand-*`。

高频影响区域包括：

- 用户端 Header、登录按钮、卡片强调区
- 首页、课程列表、课程详情、推荐页、个人中心
- Admin 后台导航、表单、表格操作区、状态强调区中的品牌主色部分
- 分页、抽屉、弹窗、搜索框聚焦态等通用组件

## 不改动边界

以下内容不纳入本次统一范围：

- 危险态、错误态使用的 `red` / `rose`
- 警示态使用的 `yellow` / `amber`
- 中性色使用的 `slate` / `gray`
- 与业务状态强相关且不属于品牌主色的标签色

这样可以确保本次改动只围绕“主题主色统一”展开，不把语义色也误并入品牌体系。

## 风险与处理

### 风险 1：改动面大，容易漏改

处理方式：

- 以全局搜索为基础，逐类替换 `indigo-*`
- 优先处理 `bg`、`text`、`border`、`ring`、`from`、`to`、`via` 等主色类名
- 通过 lint、测试和诊断辅助发现遗漏

### 风险 2：局部视觉发生细微偏差

处理方式：

- `brand` 色阶基于当前 `indigo` 观感建立
- 先保证等价替换，再对少量对比度敏感位置做微调

### 风险 3：旧变量与新 token 并存

处理方式：

- 明确 `brand` 为唯一公开主题来源
- 只保留必要的兼容映射，不保留长期双轨结构

## 验证方案

实现阶段至少需要验证以下结果：

- 项目内不再以 `indigo-*` 作为品牌主色表达
- `brand-*` 成为主色相关样式的统一命名
- 根样式中不再保留与 `brand` 并行的主色来源
- 用户端和后台主要页面视觉保持基本一致，不出现明显失真
- 构建、lint 和测试结果保持通过

## 实施顺序

建议按以下顺序执行：

1. 在 `src/index.css` 中建立 `brand` 主题 token
2. 收敛或移除 `--color-primary` 与 `--color-secondary`
3. 全量替换项目内以 `indigo-*` 表达品牌主色的类名
4. 检查局部视觉敏感组件，处理少量对比度或层级问题
5. 运行 lint、测试和诊断，确认没有遗漏或语法问题
